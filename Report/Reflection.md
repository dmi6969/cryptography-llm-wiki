## 一、作業要求問題

### Q1. 哪一個 Workflow 節點最常出錯？

> 對應老師題目：「哪一個節點最常出錯？」／「哪個 Workflow 節點最容易出錯？發生了什麼錯誤？」

**AI 建議回答（狀態：待確認）**

以 Graph 實際記錄的驗證失敗次數來看，最常出錯的是 **⑧ 產生 HTML ⇄ ⑨ HTML Validation 這個迴圈**：
- run-02 中 HTML Validation 失敗 2 次，第 3 次才通過。
- run-04（加入加密／解密圖解）、run-05 各失敗 1 次；run-07（重排為 30 張）失敗 1 次。
- run-01 和 run-04 雖然最後都通過，但 Graph 結束後看截圖，又各發現自動測試沒抓到的問題。

實際發生的錯誤：
1. 第 8 張的 ECB 示範圖，兩個顏色的對比只有 **1.06:1**，肉眼幾乎看不出鎖頭輪廓。
2. 第一次修正後，對比只提升到 **1.94:1**。原因是鎖頭像素的編碼值，加密後的亮度剛好和背景接近。用 Python 重算找出原因後，第三次修正才達到 **9.03:1**。
3. 第 9 張 DH 表格的「K = 18」被斷成兩行。

其他節點的錯誤：
- ④ Wiki Validation 失敗 1 次：236 條引文中有 1 條是跨頁引文，中間夾著 NIST 頁首，所以比對不到。
- ⑦ Content Validation 失敗 0 次。

另一個發現比「哪個節點錯最多」更重要：**檢查節點本身也會漏掉問題**。
- ② Ingestion 判定 FIPS 197 抽取成功，實際上 fi 連字全部遺失（specified 變成 specifed）。
- ⑨ 判定 HTML 通過，示範圖其實看不清楚。
- ⑦ 在自我測試中被發現「AES-128 做 12 輪」也能通過。
- 反過來，檢查也會**誤判**：run-04 加強後的 C3 把圖說「AES-128 第 1 輪」的序數當成「只做 1 輪」，內容其實沒錯。
- 手機版有 10/12 張投影片的內容蓋住來源欄，從 run-01 就存在，到 run-04 看截圖才發現。
- 最大的漏洞在「檢查標準」本身：名詞沒先解釋、公式符號沒說明、主題擠在一兩頁——所有檢查都通過，是使用者看了簡報才指出來（run-07 前）。

### Q3. 是否因此修改 Workflow / Graph？為什麼？

> 對應老師題目：「你有沒有因此修改 workflow / graph？為什麼？」

**AI 建議回答（狀態：待確認）**

有，從 v1 改成 v2，並用 run-02 重新執行整個 Graph 驗證。修改內容：
1. `ingest_sources` 加入抽取品質檢查（連字遺失）。
2. `organize_wiki` 每個 batch 寫完就做快速檢查，沒過就留在同一個 batch 修正。這是 Graph 的自我迴圈。
3. HTML Validation 加入示範圖對比度檢查。
4. Content Validation 的 C3 改為版本與輪數逐一比對。
5. Wiki 改為增量模式：已存在的節點不重建，符合 LLM Wiki「持續累積」的精神。
6. 新增 `note` 指令，把 Graph 外的人工檢查與 validator 自我測試也寫進同一份事件紀錄。
7. run-04、run-05 之後繼續調整：
   - C3 排除序數「第 N 輪」，修正誤判。
   - C4 加入 AES 實例重算。
   - H6 加入手機版內容重疊檢查。
   - H7 改為檢查實際顯示，並加入 AES 逐步圖解、Caesar 解密、分頁的檢查。
8. run-06、run-07（依使用者回饋重做）：
   - fetch 加入 curl 備援，ingest 支援 HTML 網頁。
   - 把使用者的回饋寫成 C7（名詞先解釋）、C8（公式符號）、C9（圖名不寫來源）、C10（每章來龍去脈）、H8（畫面名詞檢查）。
   - build_html 改由產生器組裝，畫面文字一律取自已驗證的內容檔。

為什麼：
- **錯誤越晚發現，修正越貴。**
  - 連字問題如果拖到 Wiki Validation，S04 相關的引文會一次全部失敗。
  - 跨頁引文要等 5 個 batch 都寫完才知道。
  - 示範圖問題甚至在 Graph 結束、判定完成之後才被發現。
- **「通過」不等於「正確」，檢查本身也需要被測試。**
  - run-01 的 Content Validation 和 HTML Validation 都是一次通過，但自我測試和人工看圖都證明，它們各自有漏洞。
- run-02 證明修改有效：同一個 ECB 問題，v1 只能靠人工發現，v2 由自動檢查擋下並退回 HTML 生成修正。

## 二、Workflow 設計與實際執行

### Q4. 為什麼選擇這樣的 Workflow？

> 對應老師題目：「請簡單說明你的流程……為什麼這樣設計？」

**AI 建議回答（狀態：待確認）**

流程是：資料取得 → Ingestion → Wiki 整理 → Wiki Validation → 查詢 Wiki → 整理教學內容 → Content Validation → 產生 HTML → HTML Validation → 完成。用 LangGraph 實際執行。

設計理由：
1. **先建 Wiki，再查詢，再生成。** 簡報只能用 `query_wiki` 查到的節點（由 C2 強制），所以每個重點都能追到「節點 → 來源頁 → 原文頁碼」。這對應評分標準的「Wiki 資料與簡報內容有明確對應」。
2. **檢查一律用程式，不讓 LLM 自己打分數。**
   - 引文必須在原文逐字找到（W5）。
   - 數值必須和事實表一致（W8／C3）。
   - 範例由程式重算（C4）。
   - 這些是專門防止 LLM 虛構的機制。
3. **失敗只退回出問題的那一層，而且有重試上限（3 次）。** 不必整條重跑，也不會無限迴圈。
4. **檢查規則先寫、內容後生成**，避免為了讓內容通過而事後放寬規則。
5. 環境沒有 LLM API Key，所以生成節點用 LangGraph `interrupt` 暫停交給 agent。分工是：Graph 負責流程與檢查，agent 負責生成。

### Q5. 哪些步驟需要重複執行？為什麼？

> 對應老師題目：「哪些步驟會重複執行？」

**AI 建議回答（狀態：待確認）**

| 會重複的步驟 | 什麼時候重複 | 實際重複了幾次 |
|---|---|---|
| ③ Wiki 整理 | 每個 batch 執行一次（共 5 次）；v2 起 batch lint 沒過就重做同一個 batch；Wiki Validation 失敗時退回修正 | run-01：5 個 batch + 1 次修正；run-04：增量更新 1 次 |
| ④ Wiki Validation | 每次 Wiki 修正後重跑 | run-01：2 次（失敗 → 通過）；run-02 到 run-05：各 1 次 |
| ⑥ 整理教學內容／⑦ Content Validation | Content Validation 失敗時 | run-01 到 run-03：0 次重試；run-04：1 次（驗證器誤判）；run-07：1 次（1 個內容錯誤＋2 個新檢查誤判）；run-09：1 次（轉場頁標題搶先用了名詞） |

為什麼要重複：生成的結果不一定一次就對，所以要「生成 → 檢查 → 退回修正」，直到通過或達到上限。設上限是為了避免無限迴圈，超過就停下來交給人判斷。

### Q6. 實際執行時遇到哪些問題？

> 對應老師題目：「完成一次實際執行後……」／「發生了什麼錯誤？」

**AI 建議回答（狀態：待確認）**

依時間順序列出全部實際發生的問題：

1. **PDF 連字遺失（Ingestion 階段的隱藏問題）。**
   - FIPS 197 的 PDF 把 fi 連字對應錯誤，抽出的文字變成 "specifed"、"confdentiality"。
   - 換用 pypdf、pdfminer.six、PyMuPDF 三套工具，結果都一樣，確認是來源檔本身的問題。
   - 解法：比對時把 fi 摺疊成 f，並在 ingest 加入偵測。
2. **AI 在 Wiki 整理時自我檢查發現的 3 個小問題**（都在驗證之前修掉）：
   - 「DES 仍是標準」的時效說明會觸發自己訂的誤解規則，所以移到「常見誤解」段落。
   - GCM 頁引用了 S05，卻沒列在來源欄。
   - Diffie–Hellman 小數字範例是自行計算的，沒有原文可引，因此不放進事實表，改由 Content Validation 重算。
3. **Wiki Validation 第 1 次失敗。** 1 條跨頁引文中間夾著 NIST 頁首，拆成兩條後通過。
4. **HTML 視覺問題。** ECB 示範圖對比不足、DH 表格斷行。自動測試沒抓到，是看截圖才發現的。
5. **對比度第一次修正不夠**（1.94:1）。用 Python 重算找到真正原因（像素編碼值）後才修好（9.03:1）。
6. **Content Validation 有漏洞。** 自我測試時，「AES-128 做 12 輪」能夠通過，已修正。

7. **（run-04）驗證器誤判。** 加強後的 C3 把「AES-128 第 1 輪」的序數當成輪數。這是唯一一次判定「內容沒錯，要改的是驗證器」。
8. **（run-04）CSS 的 `display:flex` 蓋過了 `hidden`。** 第 8 張 4 個分頁同時顯示、內容溢出。同時發現 H7 只看 `hidden` 屬性，測試本身有漏洞。
9. **（run-04 截圖 → run-05）手機版 10/12 張內容蓋住來源欄。** 這是 run-01 就存在、一直沒被發現的問題。另有兩個小問題：`①②③④` 在等寬字型中看起來像 ⊕；Caesar 字母列的 X、Y、Z 被擠出畫面。
10. **（run-06）資料取得失敗。** Cloudflare 擋下 Python 的 HTTP 用戶端（403），重試 3 次都一樣，只能中止 run-06；改成失敗時用 curl 備援。
11. **（run-07）流程順序錯誤。** 查詢 Wiki 時大綱還是舊的 12 張，更新大綱後重新查詢。
12. **（run-07）新檢查的誤判。** 「輪流」被當成名詞「輪」、「CAESAR」含有字母 AES、畫面上相鄰兩個標籤的文字黏成「公開金鑰」。
13. **（使用者回饋）教學品質問題。** 名詞沒先解釋、公式符號沒說明、Vigenère 沒解釋、每個主題擠在一兩頁——這些是自動檢查原本完全沒有規則的部分。

另外有一個環境上的小問題：在命令列傳 resume 說明時，文字裡的反引號讓 shell 出錯，改寫說明文字後解決。

### Q10. 哪些地方需要檢查或重新生成？

> 對應老師題目：「哪些地方需要檢查或重新生成？」（作業步驟三）

**AI 建議回答（狀態：待確認）**

需要檢查的地方有 3 個驗證節點，另外加上 v2 新增的 2 個提前檢查：

| 檢查點 | 檢查什麼 | 不通過時重新生成什麼 |
|---|---|---|
| ② Ingestion（v2 加強） | 下載狀態、抽取字數、關鍵字、連字遺失 | 重新抽取，或改用連字摺疊比對 |
| ③ batch lint（v2 新增） | 該 batch 頁面的格式與引文 | 重寫同一個 batch 的 Wiki 頁 |
| ④ Wiki Validation | 取得、覆蓋、引文可追溯、連結、重複、矛盾 | 修正 Wiki 頁 |
| ⑦ Content Validation | Wiki 依據、技術正確、範例、教學順序、文字量 | 重寫教學內容 |
| ⑨ HTML Validation | 開啟、內容完整、切換、頁碼與進度條、全螢幕、排版、互動、對比度 | 重寫 HTML |

此外，**驗證器本身也要定期用「注入錯誤」的自我測試檢查**，否則它們通過了也不代表內容正確。

### Q7. 這次使用 LLM Wiki 的心得

**AI 整理的可參考觀察（不是我的心得，狀態：待我補充）**
- Wiki 先把 12 篇來源整理成 20 個有引文的節點，所以做簡報時只要查 Wiki，不必再翻原始 PDF。
